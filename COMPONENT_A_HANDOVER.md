# Component A handover

Component A is a deterministic, in-memory synthetic worksite service. Implemented:
existing workers/tasks/assignments/clock, correlated environmental channels and separate
WBGT arithmetic, six engineering scenarios, atomic commands, versioned HTTP contracts,
authentication, optimistic concurrency, idempotency, OpenAPI and executable HTTP demo.
Component B and Component C are not implemented or connected.

## Install, run and verify

From this repository root, tested using Python 3.13.5:

```sh
python3 -m venv .venv
.venv/bin/python -m pip install -r requirements.lock
export PYTHONPATH=src
export HEATSHIFT_MODE=deployment
export HEATSHIFT_API_TOKEN="$(.venv/bin/python -c 'import secrets; print(secrets.token_urlsafe(32))')"
export HEATSHIFT_CORS_ORIGINS=http://localhost:5173
.venv/bin/python -m uvicorn heatshift_ai.api:create_app --factory --host 127.0.0.1 --port 8000 --workers 1
```

In another terminal (with the same token):

```sh
curl http://127.0.0.1:8000/health
curl -H "Authorization: Bearer $HEATSHIFT_API_TOKEN" http://127.0.0.1:8000/api/v1/simulation/state
```

Copy `.env.example` for your deployment environment; the application reads exported
variables, not `.env` automatically. Never commit the populated file. Run only one
process/worker and one replica. Multiple instances require shared state, a durable
idempotency ledger and coordinated writers, none of which are implemented here.
Process restart loses all in-memory state and changes instance identity.

```sh
.venv/bin/python -m pytest -q
PYTHONPATH=src .venv/bin/python examples/export_api_contract.py
.venv/bin/python examples/component_a_demo.py --output evidence.json
```

The last command starts and stops its own authenticated loopback Uvicorn server and
uses actual HTTP. It runs seed 42 with 10 workers, six assigned tasks, three work zones,
one rest zone, advances 10 seconds, activates HEAT_ESCALATION, advances 60, executes a
scripted mock B reassignment, then advances another 10. W-03 retains 70 exposure seconds;
W-06 gains 10. The client validates eligibility, requests a fixed fixture action and
checks persisted GET responses. No decision is generated by Component A. Export contains
before/after snapshots, changes, events and HTTP traces. Only random process identity is
normalized to `<service-instance>` for deterministic evidence; simulation data is intact.

Optional container recipe (provided, **not built/tested in this environment**):

```sh
docker build -t heatshift-component-a .
docker run --rm -p 127.0.0.1:8000:8000 --env-file .env heatshift-component-a
```

Docker uses the pinned lock, a non-root UID and health check. The base Python image tag
is not digest-pinned; pin your approved image digest for immutable deployment. The lock
includes test dependencies for straightforward reproducibility. No extra data service
is required. Add TLS and deployment access controls before exposing beyond localhost.

## Component B integration

1. Read `/api/v1/simulation/state` to obtain one synchronized snapshot. Collections are
   convenient views; separate GETs can have different versions if another writer acts.
2. Inspect `required_qualifications`, worker `qualifications`, `availability_status`,
   `work_status`, `current_task_id`, task status and `allowed_zone_ids`. These are explicit
   simulator attributes, not inferred health or risk scores.
3. B performs its own assessment outside A. Submit a proposed command batch with current
   simulation/instance/version, a unique idempotency key and explanatory reasons.
4. On 200 retain the returned snapshot/version/events. On 422 examine rejection and
   reconsider the proposal. On 409 read new state; do not blindly force a stale command.
5. On a network retry use the identical key/body; returned replay is the original result.
6. Interpret synthetic source, quality, observed timestamp, WBGT kind and method together.
   Null or stale is unavailable input, not zero exposure or a safety judgment.

No n8n workflow or Supabase schema was created. Future persistence can store immutable
snapshot envelopes, workers/tasks/zones, environmental channels and metadata, events,
command request/result plus idempotency key, and versioned scenario inputs. Use instance
and state versions to distinguish reset/restart and avoid mixing observations across time.
Do not store the API bearer credential in analytical records.

## Component C integration

Generate TypeScript models/client from `openapi.json`. Render one snapshot consistently,
show simulated time rather than wall-clock acquisition, label all generated values as
synthetic, display channel units and missing/stale/invalid states. Display task/worker
references and event reasons, and use instance_id/state_version to detect change. Risk
classifications/alerts must come from B, not inferred by this API. Never ship the service
write credential in frontend code; use an authorized backend integration.

## Audit and limitations

Canonical domain classes and the existing clock/assignment/transition validation remain
in use. HTTP schemas are projections, not additional mutable domain state. Added `fork`
and `activate_on` allow transaction candidates without bypassing invariants. Legacy
ScenarioController and CLI are retained compatibility interfaces; the HTTP API exclusively
uses EngineeringScenarioRunner/IntegratedSimulationEngine, with one committed clock.
No placeholder implementation or broken import was found in exercised modules. Ellipses
in Protocol declarations are intentional interface contracts.

The HTTP reset rebases an activated scenario to zero while preserving monotonic API
version and cache. Reset event namespaces prevent worker-event ID collisions. Scenario
preset switching may change initial conditions immediately; ramps inside a profile are
continuous. All earlier 333 tests remain passing. Full audit results and observed commands
are in COMPONENT_A_TEST_REPORT.md.

Synthetic natural wet-bulb is an explicit generated channel; WBGT weighting is calculated
from supplied channels. Correlations are illustrative and not field calibrated. No real
sensor connection, physical measurement claim, physiological model, occupational threshold,
risk classification or automated safety reassignment is implemented. Atomicity covers
in-memory deepcopy-able providers only, not external side effects. Events/snapshots and
idempotent responses consume memory; operation limit prevents unbounded accepted writes,
but production retention/storage and load testing remain future work. No coverage percentage
or Python-version matrix is claimed.
